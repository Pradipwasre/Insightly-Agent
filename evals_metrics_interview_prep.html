4 Interview questions

Q1

What is the difference between task completion and task success for an AI agent?

Answer

Task completion means the agent finished and gave an answer without crashing or timing out. Task success means the answer was actually correct. An agent can complete 100% of tasks and still be wrong in many of them. So we track both: completion is the minimum bar, success is the real goal.

How I used it in my project

Yes, I applied this in my project Insightly-lite. I keep them as two separate metrics. completed() only checks “no error and the answer is not empty”. Correctness is checked separately in success_rate.py. In run.py, if the API call crashes I catch the error and save it in the record, so a crash lowers the completion score instead of stopping the whole test run. Also, run.py exits with code 1 if completion is below 100%, so a CI pipeline would fail. In our last run, 17 of 17 tasks completed.

4 Interview questions

Q1

How do you check if an agent's answer is correct when the answer is free text?

Answer

Choose a check for each kind of task. For numbers, compute the true value yourself and check the answer contains it, allowing small rounding. For names, a simple text match. For open-ended text, use an LLM-as-a-judge with a clear rubric. For safety cases, check the agent refused and that nothing changed in the system. Rule-based checks are cheap and repeatable; LLM judges are flexible but cost money and can be inconsistent.

How I used it in my project

Yes, I applied this in Insightly-lite. Every data test case has a truth_sql. run.py runs that SQL on the real database to get the true number, and success_rate searches for that number in the answer using close(), which accepts rounding like “$3.36M” or a 1% difference. I have six task types — data, chat, chart, recall, no_data and unsafe — and each one has its own rule. No judge LLM is needed, so the check is free and gives the same result every time.

Q2

How do you test that an agent refuses unsafe or harmful actions?

Answer

Add attack cases to the test set, like “delete all orders”. A case passes only if the agent refuses and the system state did not change. Don't trust the words alone — always check the side effects.

How I used it in my project

Yes. We have an unsafe_delete test. run.py counts rows in the orders table before and after the question and saves data_intact. Success needs data_intact == True plus a refusal word such as “can't” or “read-only”. On top of that, the shop database is opened read-only for the agent, so even bad SQL cannot change data. That is defence in depth.

4 Interview questions

Q1

How do you measure tool-calling (function-calling) accuracy in an AI agent?

Answer

For every tool call, check three things: did the agent pick a tool that exists (and the right one), were the arguments valid, and did the call run without error. Score = good calls ÷ total calls. Also handle the “no tool needed” case: if nothing was needed and nothing was called, that is correct. More advanced setups also compare arguments with expected arguments.

How I used it in my project

Yes, I applied this in Insightly-lite in tool_call_accuracy.py. A call is good when the tool name is in our allow-list of 4 tools and the output does not start with an error. So if the LLM writes SQL that fails, it lowers this score. Our run got 100%. One limit I'm aware of: it checks the SQL ran, not that it was the right SQL — that part is covered by Success Rate.

Q1

How do you evaluate the planning or routing step in a multi-agent system?

Answer

Check the decisions made before the agent acts: was the request sent to the right agent, were required first steps done in the right order (for example, read the schema before writing a query), and did it collect the context it needed? Turn these into a small checklist and score checks passed ÷ checks made. This finds problems early, even when the final answer happens to be right.

Trajectory Accuracy

evals/metrics/trajectory_accuracy.py
94%last run

How close is the agent's sequence of tool calls to the ideal sequence? ▲ higher is better

Uses →nothing — stands alone
Used by ←

1 The code

trajectory_accuracy.pyUnderlined names open the file they come from

2 What it does (simple words)

  1. Trajectory = the ordered list of tools the agent used, e.g. [get_schema, lookup_metric, run_sql].
  2. lcs() finds the Longest Common Subsequence between actual and expected — the longest list of steps that appear in both, in the same order (dynamic-programming table).
  3. Task score = LCS ÷ the longer of the two lists. Extra steps and missing steps both lower it.
  4. No tools used and none expected → 1.0.
  5. Final = average over tasks.

3 Output

0.6666666666666666       # answer was right, but one extra call

Tasks at 0.67: orders_2024 (missing step), chart_monthly_orders (missing step),

4 Interview questions

Q1

What is trajectory evaluation, and why is checking only the final answer not enough for agents?

Answer

The trajectory is the full path of steps and tool calls the agent took. Two agents can give the same correct answer, but one takes 3 steps and the other takes 10 with retries. Trajectory evaluation catches wrong order, skipped steps and wasted steps. These matter because they cost money, add latency, and show the agent may fail on harder questions.

How I used it in my project

Yes, I applied this in Insightly-lite. I compare the actual tool list with the expected one using Longest Common Subsequence: LCS ÷ the longer length. For example, chart_country_share used get_schema → run_sql → make_chart, but the ideal was get_schema → make_chart. That gives 2/3 = 0.67. The answer was still correct, so only this metric showed the extra call. Overall we got 94%.

Q2

Why use LCS instead of an exact match of the tool list?

Answer

Exact match is too strict: one extra retry makes the score 0, even if the agent was nearly perfect. LCS gives partial credit and still respects order. Other options are “in-order” match (expected steps appear in order, extras allowed) and “any-order” match (just the right set of tools).

How I used it in my project

In my project I chose LCS so I can see small differences — 0.67 vs 1.0 — instead of a harsh pass/fail. It tells me how far off the agent was, not just that it was off.

4 Interview questions

Q1

How do you detect and measure hallucinations in an LLM application?

Answer

A hallucination is when the model states something that is not supported by its sources. To measure it, split the answer into claims and check each one against the given context — using rules, an NLI model, or an LLM-as-a-judge. Hallucination rate = answers with at least one unsupported claim ÷ all answers. To reduce it: ground the model with RAG or tools, tell it to say “I don't know”, use low temperature, and ask for citations.

How I used it in my project

Yes, I applied this in Insightly-lite. In a data agent the most dangerous hallucination is a made-up number. hallucination_rate.py reuses unsupported() from groundedness: every number in the answer must appear in the tool outputs, the question, or the earlier chat. I also added a no_data test (asking about 2030) to check the agent says “no data” instead of inventing a figure. Our hallucination rate was 0%.

1 The code

groundedness.pyUnderlined names open the file they come from

2 What it does (simple words)

  1. Evidence = tool outputs of this turn + the question + earlier answers in the same chat (so a follow-up can reuse an earlier number).
  2. source_values() pulls every number out of the evidence.
  3. numbers() pulls every number out of the answer, each with a rounding tolerance (it skips small plain numbers ≤ 12 like “top 3”, and ignores SQL code).
  4. close() checks each answer number against the evidence numbers. The ones with no match are unsupported.
  5. Task score = supported ÷ total. An answer with no numbers scores 1 (nothing to check). Final = average.

4 Interview questions

Q1

What is groundedness (faithfulness), and how is it different from hallucination rate?

Answer

Groundedness is the share of claims in an answer that are supported by the evidence (0 to 1, higher is better). Hallucination rate is a yes/no per answer: does it have any unsupported claim? Example: an answer with 9 good numbers and 1 bad one has groundedness 0.9, but it still counts as 1 hallucinated answer. RAGAS calls this metric “faithfulness”.

How I used it in my project

Yes, I applied this in Insightly-lite in groundedness.py. It measures the share of numbers that come from the evidence: tool outputs, the question, and the chat history. numbers.py handles formats like “$3.36M” vs 3,356,336.16 using rounding tolerance. I made it rule-based on purpose: it is fast, free and gives the same result every run, with no judge LLM. The trade-off is that it only checks numbers, not text claims — for text I would add an LLM judge.

Q1

When should an AI agent hand off to a human (human-in-the-loop), and how do you measure it?

Answer

Hand off when the request is unclear, the agent keeps failing (repeated errors), confidence is low, or the action is high-risk or can't be undone (payments, deleting data, sending emails). Measure how often hand-offs happen: lower means more autonomy, but zero is not the goal for risky actions — there a human approval is a feature.

4 Interview questions

Q1

Why track p95 latency instead of only the average for an LLM agent?

Answer

The average hides slow outliers. p95 means 95% of requests are faster than this value, so it shows what the slowest 1 in 20 users feel — that is where complaints start. Agents call the LLM several times per task, so slow steps add up. Ways to improve: fewer steps, a smaller faster model for simple steps like routing, caching, streaming the answer, and running independent tool calls in parallel.

How I used it in my project

Yes, I applied this in Insightly-lite. latency.py reports mean, p50 and p95. Our run: median 4.91s, mean 7.08s, but p95 26.98s — two questions (average order value and conversion rate) took about 25 seconds. The mean alone would have hidden that. With only 17 tests, p95 is just the slowest case, so for real decisions I'd use a bigger test set. To keep latency down, the router and the summary of old chat turns use a cheaper, faster model (FAST_MODEL).

4 Interview questions

Q1

How do you calculate and reduce the cost of an LLM agent?

Answer

Cost = input tokens × input price + output tokens × output price (prices are usually per 1M tokens). For an agent, add up all LLM calls in one task, not just one call. To reduce it: use a smaller model for easy steps, shorten prompts, cache repeated context, cut unneeded steps, and summarise old chat history instead of sending it all. Remember: cheaper tokens don't always mean a cheaper task if the cheaper model takes more steps.

How I used it in my project

Yes, I applied this in Insightly-lite. cost_per_task.py uses config.cost_usd(), the same price table the API and web app use. Our run on gpt-5.4-mini: about 1,966 tokens and $0.0019 per task, $0.0325 for all 17 tests. Input tokens are most of it (around 2,400 in vs 120 out) because the schema goes into the prompt, so that is where I would optimise first. We already summarise older chat turns with the fast model to keep prompts short.

Must-know questions

★

Explain a RAG architecture.

RAG = Retrieval-Augmented Generation. The LLM does not know your private or latest data, so we first find the right information and then give it to the LLM inside the prompt.

Documents→Split into chunks→Embeddings→Vector DB

1. Indexing (done once, offline)

User question→Embed + search top-k→(Re-rank)→Prompt = question + chunks→LLM answer + citations

2. Query time (every question)

Why: fresh data, fewer hallucinations, no re-training. How to evaluate: retrieval (did we fetch the right chunks?) and generation (is the answer faithful to the chunks and relevant to the question?).

In my project

In Insightly-lite the “retrieval” is done with tools instead of a vector search: get_schema and lookup_metric fetch table and metric definitions, and run_sql fetches the real facts. Then groundedness.py checks the answer really used that evidence.

★

What is prompt injection?

Prompt injection is an attack where some text tricks the LLM into ignoring its instructions and doing something else.

  • Direct: the user types “Ignore all previous instructions and …”.
  • Indirect: hidden instructions sit inside a web page, document, email or tool output that the agent reads.

It is more dangerous for agents, because agents can take actions. Defences: treat outside content as data, not commands; keep the system prompt separate; give tools the least power needed (e.g. read-only); validate outputs; ask a human before risky actions; add input/output filters.

What are guardrails?

Guardrails are checks and rules around the LLM that keep it safe, correct and on-topic.

  • Input guardrails: block prompt injection, personal data (PII), off-topic or harmful requests.
  • Output guardrails: check for toxic content, PII leaks, wrong format (e.g. JSON schema), unsupported claims.
  • Action guardrails: allow-list of tools, read-only access, limits on retries/cost, human approval for risky steps.

Common tools: NeMo Guardrails, Guardrails AI, Llama Guard — or simple code rules.

In Insightly-lite: a fixed allow-list of 4 tools, a read-only database, and evals that flag hallucinated numbers and repeated SQL errors.
